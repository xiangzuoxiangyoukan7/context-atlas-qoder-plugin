# Schema 字段说明

## Schema 是什么

Schema 是数据的“填写规则”，作用类似数据库表结构或表单校验规则。例如 `feature.schema.json` 规定功能卡必须有编号、标题、状态、优先级和验收引用。检查器读取 Schema 后，能发现缺字段、状态值非法、编号格式错误等问题。

Schema 只能证明结构符合规则，不能证明业务内容正确。业务内容仍由来源证据、Proposal 和用户确认保证。

## 轻量 Schema 中的规则元素

| 元素 | 作用 | 示例 |
| --- | --- | --- |
| `required` | 文件必须包含的字段；缺少任何一个都会报错 | `id`、`title` |
| `enums` | 某个字段只能从给定值中选择 | `status` 只能是 `draft`、`approved` 等 |
| `patterns` | 字符串必须符合正则格式 | 新功能编号必须类似 `F-ORDER-001` |
| `non_empty_lists` | 列表必须至少有一个成员 | `sources` 不能为空 |
| `unique_lists` | 列表成员不能重复 | 同一个来源不能重复登记 |
| `list_enums` | 列表中的每个成员都必须来自允许值 | `source_types` 的每一项都受限制 |

Markdown 文件中的字段位于文件顶部：

```yaml
---
id: F01
type: feature
title: 用户登录
status: approved
---
```

## 每个文件负责什么

### `catalog.json`

Schema 总目录。键是知识类型，值是负责校验该类型的 Schema 文件。例如 `feature` 指向 `feature.schema.json`。检查器只从这里发现轻量 Schema，避免目录中任意 JSON 被误当作知识类型。

### `project-manifest.schema.json`

约束知识库根目录的 `knowledge-base.yaml`。

| 字段 | 作用 |
| --- | --- |
| `project_id` | 项目稳定机器编号 |
| `project_name` | 项目显示名称 |
| `knowledge_base_name` | 知识库目录名，必须以 `doc-` 开头 |
| `workspace_profile` | 可选工作区显示配置；初始化产物为 `standard` 或 `obsidian` |
| `project_version` | 当前项目版本 |
| `format_version` | 知识库磁盘格式版本，用于兼容和迁移；格式 13 将决策依据归入所属知识，不再使用独立 ADR |
| `knowledge_revision` | 正式知识事务成功后的单调修订号 |
| `created_by` | 可选生成工具追踪信息，不参与兼容判断 |

### `knowledge-item.schema.json`

约束没有专用类型 Schema 的通用知识项。

| 字段 | 作用 |
| --- | --- |
| `id` | 稳定知识编号 |
| `type` | 固定为通用知识类型 |
| `title` | 人类可读标题 |
| `status` | 草稿、已批准、已弃用等生命周期状态 |
| `content_revision` | 同一稳定知识身份的内容修订；旧 `version` 在兼容周期内仍可读取 |
| `sources` | 支撑该知识的来源编号列表 |
| `last_updated` | 最后更新时间 |

### `feature.schema.json`

约束功能卡。

| 字段 | 作用 |
| --- | --- |
| `id` | 功能编号 |
| `type` | 固定为 `feature` |
| `title` | 功能名称 |
| `status` | 功能生命周期状态 |
| `phase` | 所处阶段 |
| `priority` | 优先级 |
| `current_slice` | 是否属于当前交付切片 |
| `depends_on` | 依赖的功能或知识编号 |
| `acceptance` | 对应验收项编号 |
| `contracts` | 格式 1 至 9 的遗留字段；格式 10 功能改用 `rel_*` 关联具体技术对象 |
| `last_updated` | 最后更新时间 |

功能、模块和接口可以增加三个相互独立的规格字段：`approval_status` 表示内容是否批准，`lifecycle_status` 表示是否为当前有效知识，`spec_readiness` 表示是否足以进入下一阶段。格式 12 的需求改用简化字段 `status` 与 `readiness`；批准、现行和规格完整仍不能相互推导。

### `requirement.schema.json`

约束需求知识。需求使用 `REQ-<领域>-<三位序号>` 稳定编号；Front Matter 只保存 `id`、`type`、`title`、`status`、`readiness`、`priority`、`rel_classified_under` 和 `last_updated`。问题价值、范围、`BR-*` 业务规则、`SC-*` 成功标准、约束依赖、`BQ-*` 阻塞问题和来源确认保存在正文稳定章节。实现它的功能可以通过 `rel_satisfies` 正向引用需求；没有功能承接不影响需求自身成为 `ready`。

### `module.schema.json`

约束模块边界契约。模块使用 `MOD-*` 稳定编号，记录代码路径、职责、明确不负责内容及依赖边界；功能通过主模块和参与模块关系关联。

### `interface.schema.json`

约束统一接口契约。`interface_kind` 区分 HTTP、RPC、事件、Webhook、文件和函数，`visibility` 区分内部与外部；每项接口具有独立版本、来源及兼容策略。

### `contract.schema.json`

约束不属于单一模块、接口或数据对象，并且至少具备多方复用、跨边界、独立版本、独立责任方或脱离单一功能继续有效之一。`independence_basis` 声明独立依据；局部约束必须保留在所属知识文件。跨项目标准只保存权威来源、采用版本和本地差异。

### `task.schema.json`

约束产品开发任务。

| 字段 | 作用 |
| --- | --- |
| `id` | 任务编号 |
| `type` | 固定为产品任务类型 |
| `title` | 任务标题 |
| `feature` | 任务服务的功能编号 |
| `status` | 待处理、进行中、完成等状态 |
| `acceptance` | 任务必须满足的验收编号 |
| `last_updated` | 最后更新时间 |

### `governance-task.schema.json`

约束知识治理任务，而不是产品开发任务。

| 字段 | 作用 |
| --- | --- |
| `id` | 治理任务编号 |
| `type` | 固定为治理任务类型 |
| `title` | 治理任务名称 |
| `plan` | 对应治理计划或处理方案 |
| `status` | 治理任务状态 |
| `acceptance` | 完成该治理任务的验收条件 |
| `last_updated` | 最后更新时间 |

### `acceptance.schema.json`

约束验收项。

| 字段 | 作用 |
| --- | --- |
| `id` | 验收编号 |
| `owner` | 验收责任人 |
| `condition` | 需要满足的可观察条件 |
| `result` | 未验证、通过或失败 |
| `evidence` | 支撑结果的证据引用 |
| `version` | 验收适用的项目版本 |

### `acceptance-contract.schema.json`

约束实现前定义的验收场景。它通过 `subject_id` 和 `behavior_id` 标识被验证对象与规范行为，`verification_kind` 区分自动、人工、检查和指标验证；正文必须保留前置条件、WHEN、THEN 和验证方式。实际结果和证据不写入契约。

### `specification-change.schema.json`

约束一个具有单一意图的变更工作区记录，包括来源系统、受影响知识、Delta 路径、验收引用和独立变更生命周期。外部系统状态不构成正式知识批准。

### `specification-delta.schema.json`

约束 `ADDED`、`MODIFIED`、`REMOVED`、`RENAMED` 和 `SUPERSEDED`。修改必须提供完整新规格，删除必须记录原因、迁移和回滚，重命名或替代必须声明后继项。

### `source.schema.json`

约束旧格式和公共去重场景中的知识来源记录。新初始化使用内嵌来源对象；每个来源至少包含 `type`、精确 `reference`、`observed_at` 和 `confirmation_status`，已确认来源还必须包含 `confirmed_at`。初始化器把这些字段直接写入被支撑文档，独立来源记录不得成为理解单项知识的前置条件。

| 字段 | 作用 |
| --- | --- |
| `id` | 来源编号 |
| `type` | 固定为 `source` |
| `title` | 来源名称 |
| `source_type` | 用户陈述、仓库文件、命令输出、外部文档或 AI 推测 |
| `reference` | 可定位的文件、命令、文档或确认说明 |
| `last_updated` | 来源最后登记时间 |

### `knowledge-proposal.schema.json`

约束用户明确要求持久记录的单条待确认知识，不是初始化整个知识库的 Proposal。

| 字段 | 作用 |
| --- | --- |
| `id` | 提案编号 |
| `type` | 固定为 `knowledge_proposal` |
| `title` | 提案标题 |
| `status` | proposed、confirmed、rejected 或 applied |
| `checkpoint` | 在用户决定、需求变化、交付前等哪个检查点捕获 |
| `content_digest` | 提案内容 SHA-256，用于发现内容变化 |
| `target_ids` | 提案准备影响的知识编号 |
| `source_type` | 提案来源类型 |
| `source_reference` | 来源定位信息 |
| `proposed_by` | 提案人或 Agent 编号 |
| `operated_by` | 执行采集的 Agent 编号 |
| `confirmed_by` | 确认人；未确认时使用约定的空值 |
| `git_commit` | 关联代码提交 |
| `project_version` | 关联项目版本 |
| `captured_at` | 捕获时间 |

### `data-asset.schema.json`

约束业务数据资产。

| 字段 | 作用 |
| --- | --- |
| `id`、`type`、`title` | 数据资产身份 |
| `status`、`version` | 生命周期和版本 |
| `sources` | 格式 4 及后续格式的内嵌来源对象列表；旧格式可读取来源编号并通过迁移器转换 |
| `owner` | 数据责任人 |
| `source_types` | 数据来自数据库、接口、文件等哪些类型 |
| `sensitivity` | 公开、内部、敏感等分级 |
| `retention` | 数据保留规则 |
| `last_updated` | 最后更新时间 |

### `data-source.schema.json`

约束一个数据库产品或其他数据来源连接的逻辑描述，不保存密码。

| 字段 | 作用 |
| --- | --- |
| `id`、`type`、`title` | 数据源身份 |
| `status` | 当前是否有效 |
| `product`、`product_version` | PostgreSQL、Oracle 等产品及版本 |
| `owner` | 维护责任人 |
| `config_reference` | 非敏感配置所在位置，不是连接密码 |
| `environments` | 开发、测试、生产等适用环境 |
| `sources` | 支撑信息的内嵌知识来源对象 |
| `last_updated` | 最后更新时间 |

### `database-unit.schema.json`（复杂拓扑可选）

约束数据库产品下的数据库、实例或服务单元。

| 字段 | 作用 |
| --- | --- |
| `unit_kind` | database、instance、service 等单元类型 |
| `physical_name` | 实际物理名称 |
| `rel_belongs_to` | 所属数据源编号 |
| 其他公共字段 | 身份、状态、版本、责任人、来源和更新时间 |

### `database-namespace.schema.json`（复杂拓扑可选）

约束数据库单元下的 schema、catalog 或逻辑命名空间。

| 字段 | 作用 |
| --- | --- |
| `namespace_kind` | schema、catalog 等命名空间类型 |
| `physical_name` | 数据库中的真实名称 |
| `rel_belongs_to` | 所属数据库单元编号 |
| 其他公共字段 | 身份、状态、版本、责任人、来源和更新时间 |

### `database-table.schema.json`

约束数据库表。

| 字段 | 作用 |
| --- | --- |
| `physical_name` | 数据库中的真实表名 |
| `sensitivity` | 表数据敏感级别 |
| `ddl_sources` | DDL 或迁移脚本来源 |
| `rel_belongs_to` | 默认指向所属数据源；复杂拓扑中可以指向独立命名空间 |
| 其他公共字段 | 身份、状态、版本、责任人、来源和更新时间 |

### `relation-catalog.json`

它不是字段 Schema，而是关系类型目录。它规定 `rel_depends_on`、`rel_supported_by` 等关系允许从哪类知识指向哪类知识，防止方向写反或使用未声明关系。

## 初始化专用标准 JSON Schema

标准 JSON Schema 使用以下常见元素：

| 元素 | 作用 |
| --- | --- |
| `$schema` | 声明采用哪个 JSON Schema 标准版本 |
| `$id` | Schema 的稳定标识 |
| `title` | Schema 的显示名称 |
| `type` | 数据必须是对象、数组、字符串或整数等哪种类型 |
| `properties` | 对象允许出现哪些字段，以及每个字段的规则 |
| `required` | 哪些字段必填 |
| `additionalProperties: false` | 禁止未声明字段，避免 Agent 偷偷增加自由字段 |
| `enum` | 只能选择列出的值 |
| `const` | 只能等于一个固定值 |
| `pattern` | 字符串必须符合正则格式 |
| `items` | 数组中每个成员必须符合什么规则 |
| `$defs` | 可复用的内部结构定义 |
| `$ref` | 引用 `$defs` 中的结构，避免重复 |
| `allOf` | 必须同时满足多组规则 |

### `initialization-proposal.schema.json`

约束初始化前经用户确认的完整提案。

- `operation`：固定为 `initialize`。
- `proposal_revision`：对 Proposal 规范内容计算出的 SHA-256。
- `project`：项目根目录、项目编号、显示名称、目标知识库名称，以及可选的 `workspace_profile`；省略时按 `standard` 处理。
- `agent_entry`：可选的宿主入口文件策略；`codex`、`qoder`、`trae` 使用 `AGENTS.md`，`claude` 使用 `CLAUDE.md`。只有确认该字段时才创建或补充入口文件。
- `facts.goals`：已经发现或提出的项目目标。
- `facts.boundaries_in`：确认包含在项目范围内的内容。
- `facts.boundaries_out`：明确排除的内容。
- `facts.technology_stacks`：技术、版本、目录、用途、命令和配置位置。
- 项目命令不作为独立开发指南事实组；如有沉淀价值，记录在 `facts.technology_stacks[].commands` 或相关技术契约中。
- `unknowns`：尚未确认的问题。
- `conflicts`：来源之间互相冲突的内容。
- `source.type`：事实来自仓库文件、用户陈述、已有文档、命令输出或 AI 推测。
- `source.reference`：可以回查的具体位置。
- `status`：`confirmed` 表示可写为正式事实，`proposed` 表示仍待确认。

AI 推测不能直接标记为 `confirmed`。任何 Proposal 内容变化都会改变 `proposal_revision`，需要重新确认。

### `initialization-report.schema.json`

约束初始化执行器的最终输出。

- `operation`：初始化成功为 `initialized`，失败为 `failed`。
- `project_root`：实际操作的项目绝对路径。
- `knowledge_base`：实际知识库绝对路径。
- `proposal_revision`：本次执行的 Proposal 修订摘要。
- `confirmation`：确认状态和实际确认的修订号。
- `execution`：实际执行模式以及由宿主或执行器记录的运行时探测证据；可为 `python_executor` 或 `agent_host`。
- `written_files`：真正写入的文件清单。
- `technology_stacks`：实际渲染的技术栈。
- `validation`：验证结果、验证权威、确定性验证状态、命令、退出码、问题数量和逐项检查结果。`agent_host` 模式必须使用 `deterministic_validation: not_run`。
- `unknowns`、`conflicts`：仍需处理的编号。
- `next_action`：唯一明确的下一步。

Agent 只能根据这份结构化报告宣称初始化成功，不能根据对话感觉自行判断。

### `ingest-report.schema.json`

约束显式调用 `context-atlas-ingest` 后返回的只读会话报告，不约束知识库 Markdown，也不登记到 `catalog.json`。

- `operation`：固定为 `ingest`。
- `status`：来源完成分析为 `analyzed`，前置条件不满足为 `blocked`。
- `source_identity`：唯一主来源的类型与精确定位；不允许 `ai_inference` 作为主来源。
- `observed_at`、`source_digest_or_version`：来源观察时间和用于区分版本的摘要或标识。
- `scope`：本轮实际读取的知识范围。
- `candidates`：`add`、`revise`、`retire`、`conflict` 或 `ignore` 候选及其事实、推断、未知项、关系、影响和理由。
- `route_plan`：建议用户后续显式调用的维护 Skill 组合，不表示已经调用。
- `blocked_reasons`：多来源、不可定位、敏感内容、知识库缺失或格式不兼容等阻塞原因。
- `writes_performed`：固定为 `false`。
- `confirmation_state`：固定为 `not_applicable`。
- `next_action`：唯一明确的下一步。

摄取报告不是正式 Proposal、批准事实或写入许可，不得保存秘密或未脱敏个人数据。

### `batch-ingest-report.schema.json`

约束批量摄取的汇总报告；实际分析仍限 1～20 个独立来源，超限请求使用完整的阻塞报告表达。

- `source_count`：请求中的来源数量，最少 1 个；`analyzed` 报告最多 20 个，超限的 `blocked` 报告保留实际请求数量。
- `reports`：逐来源完整 `ingest-report`；单项阻塞不删除其他来源结果。批次在逐项分析前整体拒绝时为空数组。
- `route_plan`：逐来源维护路由去重后的汇总，不自动调用维护 Skill。
- `writes_performed`：固定为 `false`，表示批次不写正式知识。
- `confirmation_state`：固定为 `not_applicable`。

### `managed-source.schema.json`

约束确认保存的外部来源登记卡。`original_reference` 保留暂存定位，`managed_path` 指向固定受管文件，`sha256` 和 `size_bytes` 证明文件身份；登记卡批准的是保存行为，不批准文件正文中的业务结论。
