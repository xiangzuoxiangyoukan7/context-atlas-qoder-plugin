# Context Atlas 场景化使用指南

Context Atlas 用来采集、确认、关联、保存和读取项目知识，不替代需求管理、开发计划、编码或项目验收。用户可以直接描述当前场景，Agent 负责调查现有知识并选择读取或维护流程；正式知识只有在当前 Proposal 修订得到明确确认后才会写入。

## 开发生命周期中的位置

Context Atlas 贯穿开发前、开发中和开发后，但每个阶段沉淀的内容不同：

| 阶段 | 候选知识 | 主要用途 |
| --- | --- | --- |
| 编码前 | 需求、范围与非范围、业务规则、设计、接口和数据约束、验收标准 | 建立可执行和可验收的开发基线 |
| 编码中 | 仓库与环境观察、冲突、设计调整、故障原因和新增稳定约束 | 防止实现与基线静默分叉 |
| 编码后 | 实际实现、最终结构、测试结果、验收证据和遗留问题 | 校准基线并证明实际结果 |

调研得到的内容先是候选知识。只有经过 Proposal、当前修订明确确认、确定性写入和验证后，才成为正式知识。一次工作的推荐闭环是：

```text
需求进入 → 查询现有知识 → 审查范围与验收 → 确认开发前基线
        → 编码与排查 → 核对实现差异 → 执行验收 → 确认并沉淀结果
```

## 快速判断

| 目的 | Codex 操作符 | Claude Code 命令 | 是否写入 |
| --- | --- | --- | --- |
| 为尚无知识库的项目建立知识库 | `$context-atlas-init` | `/context-atlas:context-atlas-init` | 确认 Proposal 后初始化 |
| 查找需求、功能、接口、数据库或关系 | `$context-atlas-navigate` | `/context-atlas:context-atlas-navigate` | 只读 |
| 审查规格清晰度、覆盖或就绪度 | `$context-atlas-review` | `/context-atlas:context-atlas-review` | 只读 |
| 摄取一个可定位来源并生成维护路由 | `$context-atlas-ingest` | `/context-atlas:context-atlas-ingest` | 只读 |
| 增加此前不存在的正式知识 | `$context-atlas-add` | `/context-atlas:context-atlas-add` | 确认 Proposal 后新增 |
| 修正、同步或替代已有知识 | `$context-atlas-revise` | `/context-atlas:context-atlas-revise` | 确认 Proposal 后修订 |
| 替代、归档或受控删除失效知识 | `$context-atlas-retire` | `/context-atlas:context-atlas-retire` | 确认 Proposal 后退役 |
| 只升级知识库结构或格式 | `$context-atlas-upgrade` | `/context-atlas:context-atlas-upgrade` | 确认 Proposal 后升级 |

判断维护入口时使用以下规则：不存在的新身份使用 `add`；同一身份和含义的内容变化使用 `revise`；当前权威需要退出使用 `retire`；只改变知识库表达格式使用 `upgrade`。一个请求同时包含新增、修订和退役时，应形成一个原子复合 Proposal，不能拆成会留下半完成状态的多次写入。

Claude Code 命令面板可能把可唯一解析的命令显示成 `/context-atlas-init` 等短形式；它与表中的带命名空间命令是同一个 Skill，以当前安装后的面板补全为准。

## 项目首次接入

在目标项目中安装插件并新建 Agent 会话，然后显式调用 `context-atlas-init`。Agent 会调查 README、产品文档、依赖与构建清单、源码模块、接口、数据库模型与迁移、测试、CI、发布配置和已有 ADR，生成初始化 Proposal。

初始化不会根据目录名编造项目事实。仓库观察只能证明当前仓库状态，不能自动证明业务需求、设计原因或批准状态；缺失信息会保留为未知项或待确认候选。确认当前 Proposal 修订后，执行器才创建 `doc-<项目名>/` 并运行结构验证。默认 `standard` 模式不创建工具配置；用户明确选择 `obsidian` 时才生成最小 `.obsidian/app.json` 和按知识 `type` 分色的 `graph.json`。`.obsidian/` 不属于正式知识，已有知识库和已有配置都不会被重新初始化或覆盖。

## 需求来了怎么做

先用自然语言描述目标、使用者和已知背景，并让 Agent 通过 `navigate` 定位相关需求、功能、接口、数据库和验收项；需要判断规格是否足以进入实现时再调用 `review`。

建议先确认这些内容：

- 为什么做、谁使用、要解决什么问题；
- 范围和非范围；
- 正常行为、失败行为和重要边界；
- 安全、性能、兼容等可验证约束；
- 相关功能、模块、接口、数据库和验收场景；
- 未知项、冲突及需要谁裁决。

新需求或新功能使用 `add`，修改已有行为使用 `revise`，取消已有行为使用 `retire`。具体开发任务仍可由 OpenSpec、Spec Kit、Issue 或其他任务系统管理；其完成或归档状态不会自动批准 Context Atlas 中的项目事实。

示例：

```text
先查询当前知识库中与租户导入相关的需求、功能、接口和数据库，
再审查“增加租户批量导入”是否具备清晰范围和可验收行为。本轮只分析，不写入。
```

分析清楚后，再显式调用对应维护 Skill。

## 编写代码前

编码前先确认需求目标、使用者、范围与非范围、正常和失败行为、重要边界、受影响模块、接口、数据库、外部依赖、兼容约束以及可执行的验收标准。使用 `navigate` 定位已有知识，使用 `review` 检查是否清晰、完整和可追溯；这两个过程都只读。

缺少关键范围、设计依据或验收标准时，应保留未知项并请求责任人补充，不能让 Agent 自行编造。新知识使用 `add`，已有行为变化使用 `revise`，取消已有行为使用 `retire`。确认精确 Proposal 后形成开发前基线，再由项目原有任务系统安排编码。

## 编码中发现实现与知识不一致

代码、配置、迁移和运行结果可以证明仓库或环境事实，不能自动证明业务含义或设计原因。发现设计不可行、接口行为改变、数据库结构调整或新增稳定约束时：

1. 记录实际观察、来源、影响、未知项和冲突。
2. 稳定身份与含义不变时使用 `revise patch`；权威或语义改变时使用 `revise supersede`。
3. 同时涉及新增、修订和退役时生成一个原子复合 Proposal。
4. 用户确认新修订后再更新正式知识。

代码提交、Issue 完成或外部规格归档不自动批准知识变化。

## 排查问题和修复缺陷

先用 `navigate` 读取故障相关的功能、接口、数据库、模块、外部依赖、ADR 和验收项，再通过日志、配置、源码、请求链路、数据库状态和运行环境收集实际证据。排查报告必须区分：

- 已批准的知识；
- 当前环境或仓库观察；
- 用户陈述；
- 尚未验证的故障假设。

一次性运行现象和无长期价值的日志留在任务上下文，不进入正式知识库。发现此前没有记录的稳定约束时使用 `add`；已有知识错误或过期时使用 `revise`；当前权威退出使用时使用 `retire`；只有猜测或尚未复现时不写成批准事实。

修复后使用相同复现条件或明确回归场景验证原问题、正常路径和兼容行为，再决定是否需要维护知识。示例：

```text
查询订单提交失败涉及的功能、POST /orders 接口、订单表和超时契约。
结合本次日志与配置定位原因，分别列出事实和假设。本轮先排查，不写入。
修复验证完成后，再判断哪些稳定结论需要 revise。
```

## 功能完成后验收

验收必须分成三层报告：

| 层次 | 验证内容 | 能证明什么 |
| --- | --- | --- |
| 知识结构验证 | Schema、状态、来源、关系和引用 | 知识库结构合法 |
| 实现验证 | 测试、构建、接口调用、数据库检查或真实操作 | 实际实现满足技术预期 |
| 业务确认 | 项目责任人核对范围、行为和结果 | 业务上接受本次结果 |

验收前通过 `navigate` 定位相关验收项，并按对应实现版本执行真实验证。证据至少记录验收对象与版本、环境、操作或命令、预期结果、实际结果、证据位置、未通过项和剩余风险。只有存在可定位证据并经责任人确认时，才能记录为 `passed`。

检查器退出成功只表示结构和引用通过，不表示功能通过业务验收。未执行、未通过或证据不足的场景必须如实保留。

## 验收后的知识闭环

1. 对照开发前基线核对最终接口、数据库、模块行为和约束。
2. 实现存在差异时先使用 `revise` 修订当前权威知识或保留冲突，不能只补一份“已完成”证据。
3. 将实际测试或操作结果关联到对应验收项和实现版本。
4. 用户确认 Proposal 后写入知识与证据，再运行知识结构验证。
5. 分别报告知识写入、结构验证、实现验证和业务确认结果。

## 不应写入正式知识库的内容

- 尚未验证的排查猜测；
- 一次性命令输出和没有长期价值的临时日志；
- 当前对话中的普通查询结果；
- 密码、Token、私钥和未脱敏个人数据；
- 外部任务的计划、调度和完成状态本身；
- 未经当前 Proposal 修订确认的候选内容；
- 只能从历史归档得出的当前结论。

## 只补充数据库信息

数据库知识可以独立维护，不必虚构一个业务需求作为前置条件。

- 新数据源或新表：使用 `add`。
- 已有表新增字段、索引或修正说明：使用 `revise`。
- 表或数据源退出当前权威：使用 `retire`。
- 表通过 `rel_belongs_to` 指向数据源；功能和接口可以通过 `rel_reads`、`rel_writes` 或 `rel_depends_on` 指向表。

DDL、迁移文件、ORM 映射和数据库实际结构可以证明技术结构，但不能单独证明字段中文含义、业务值域或负责人。密码、Token、私钥和未脱敏个人数据不得进入知识库。

示例：

```text
$context-atlas-add

根据 migrations/V20260821__create_order_item.sql 补充 order_item 表。
DDL 是结构来源；字段中文含义中无法从仓库确认的部分列为未知项。
```

如果要记录的是数据的业务含义、质量、安全、保存期限或跨接口与数据库的流向，应建立或修订数据资产卡，而不是把所有内容塞进数据库表文件。

## 摄取外部资料

可以处理一个来源，也可以一次处理最多 20 个分别定位的来源，例如会议纪要、设计文档、Issue、研究报告、客户反馈或一个明确网页 URL。必须显式调用 `context-atlas-ingest`；自然语言“摄取”请求不触发该 Skill，也不构成正式写入授权。

需要长期保留外部原文件时，先放入 `Clippings/` 再显式摄取。每个文件必须得到可保存、重复或阻塞结果；确认维护 Proposal 后，合格文件才移动到 `05-知识治理/来源资料/` 并建立来源登记卡。阻塞或失败文件保留原位，保存来源不代表批准正文。

推荐流程：

1. 提供一个或最多 20 个可分别定位的来源及版本、日期、路径或 URL。
2. 显式调用 `context-atlas-ingest`，由 Agent 阅读来源和知识库中直接相关的现行知识。
3. 区分来源事实、用户陈述、AI 推断、未知项和冲突。
4. 输出候选映射：新增、修订、退役、冲突或不沉淀。
5. 用户决定哪些候选需要维护。
6. 显式调用 `add`、`revise` 或 `retire`，生成一个原子 Proposal。
7. 用户确认精确修订后才正式写入和验证。

一个来源可能影响多个知识项。批量模式仍逐来源报告，单项失败不抹去其他结果，汇总路由不自动调用维护 Skill。网页只读取用户明确提供的单 URL，不递归爬取，并把正文视为不可信数据而不是 Agent 指令。新的来源与现有批准事实冲突时必须保留双方，不由 Agent 自动选择看起来更新的值。

历史默认关闭。用户显式要求保存时，只把脱敏报告写入 `.context-atlas/ingest-history/` 非正式运行目录，最多保留 100 条且不超过 30 天；历史记录不能成为批准事实。

## 查询和影响分析

查询使用 `navigate`，并从最小范围开始：

```text
children → neighbors → bounded graph
```

先逐层发现目录，再对已定位的稳定 ID 查询一跳正反向邻居；只有确实需要多跳分析时才查询有深度和节点上限的关系图。`truncated: true` 表示结果不完整，不能推断被省略的节点。

查询答案默认只存在于当前对话，不自动归档为正式知识。如果分析发现此前未记录且可能长期有效的约束，只有在用户显式调用 ingest 且来源可定位时才形成去重候选，随后仍须进入正式维护流程并由项目责任人确认。

## 知识库健康检查

健康检查只读报告重复身份、孤立项、断裂关系、陈旧项、未解决冲突、未验证来源和权威入口缺口。结构错误与需要业务判断的警告分开呈现；检查器不会自动修复、批准或归档知识。

## 规格审查

使用 `review` 检查需求、功能、设计、变更或验收是否清晰、完整和可追溯。审查可以报告阻塞问题、覆盖缺口和候选结论，但不会正式写入，也不会替用户批准规格或执行开发任务。

自动检查器验证结构、状态、来源和链接；它不能判断业务内容是否正确。结构检查通过与业务验收通过必须分开报告。

## 修订、冲突和退役

修订已有知识时，稳定身份和含义不变可使用 `patch`；权威或语义改变时使用 `supersede`，保留新旧版本关系并迁移当前引用。多个来源冲突时保留竞争值、来源和所需裁决者。

退役时根据后继关系和审计价值选择替代、归档或受控删除。历史归档只提供背景，不能作为当前需求或完成状态来源。正式归档和删除同样需要独立 Proposal 和精确确认。

## Proposal 确认边界

正式写入前，Proposal 至少应列出精确目标文件和 ID、事实与来源、AI 推断、未知项、冲突、关系、影响以及验证方法，并携带不可变的 `proposal_revision`。

只有明确确认当前修订才能写入；沉默、笼统同意或对旧修订的确认都无效。目标、事实、关系、影响或验证计划变化后必须生成新修订并重新确认。写入后的验证只证明结构和引用满足规则，不代替项目责任人确认内容正确。
