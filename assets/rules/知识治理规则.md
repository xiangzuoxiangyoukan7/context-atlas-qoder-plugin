# 知识治理规则

本文件是首期规则正文的唯一中文权威来源。其他文件只能引用规则编号和本文件位置，不得复制后形成另一份权威正文。

<a id="RULE-CODE-001"></a>
## RULE-CODE-001 Python 代码必须具有说明和类型标注

每个 Python 模块、类、方法和函数必须具有文档字符串；参数、返回值、类属性和数据属性必须具有类型标注。生成副本必须由权威源同步，不得单独补注释形成分叉。

<a id="RULE-CODE-002"></a>
## RULE-CODE-002 Python 说明必须覆盖用途、场景和关键逻辑

每个 Python 脚本必须在模块开头用中文文档字符串同时说明“这个文件做什么”和“什么场景使用它”。每个类、方法、函数和属性都必须有可理解的中文说明；属性说明可以使用字段注释或由所属类文档逐项解释，不能只有类型而没有业务含义。重要方法必须在文档字符串中说明输入、输出和主要逻辑顺序。权限门禁、防覆盖、路径安全、原子替换、状态转换、异常恢复、数据删除和验证判断等非直观关键点，必须使用行内注释解释设计原因，不能只复述代码动作。空泛的“处理数据”“执行操作”或机械重复名称不算有效说明。

<a id="RULE-GOV-001"></a>
## RULE-GOV-001 每条正式规则只有一个中文权威来源

每条正式规则必须有稳定编号、中文名称和唯一权威段落。规则目录只保存索引与执行映射；Skill、Schema、模板、检查器和验收只负责落实规则。生成或复制到插件包的内容属于发布产物，不能独立编辑为第二套规则。

<a id="RULE-GOV-002"></a>
## RULE-GOV-002 规则使用方主动引用并接受覆盖检查

使用规则的文件必须保存 `[[rules/知识治理规则#规则编号|规则编号]]` 形式的正向引用。覆盖检查扫描正向引用生成反向索引，验证编号、文件、锚点及规则目录要求的执行载体类型。规则变化时，反向索引用于产生候选影响清单；不能在权威规则中手工维护使用方清单。

<a id="RULE-GOV-003"></a>
## RULE-GOV-003 当前变更是可选知识而不是任务执行门禁

知识库可以记录零个或多个当前变更，用于说明正在发生的项目知识变化并关联外部任务。是否执行开发任务由用户和实际任务管理工具决定；知识库不得维护任务包、执行看板或以缺少当前变更为由阻止其他插件或 Agent 执行任务。

<a id="RULE-REL-001"></a>
## RULE-REL-001 关系必须同时引用目标文件和稳定知识编号

所有正式 `rel_*` 关系值必须指向实际文件，并明确目标稳定知识编号；聚合文档还必须使用对应标题锚点。关系类型必须登记后使用。引用方向由上层业务知识指向数据库等基础知识，基础知识不反向维护全部上层使用方；反向关系由检查器计算。

<a id="RULE-REL-002"></a>
## RULE-REL-002 关系只保存统一的权威正向链接

正式关系必须使用扁平字段 `rel_<type>`，每个值统一写成 `[[相对/目标文件#可选锚点|TARGET-ID]]`。禁止同时保存裸编号关系、嵌套 `relations` 或人工反向列表。文件移动时必须更新正向链接；检查器根据正向链接实时生成反向索引，使 Obsidian 图谱和机器分析使用同一份关系事实。

<a id="RULE-SRC-001"></a>
## RULE-SRC-001 正式知识和质检结果必须引用来源与目标

正式事实必须通过 `rel_supported_by` 引用带文件路径和 `SRC-*` 编号的来源实体。纯 AI 推测只能形成待确认提案，不能单独支撑已批准事实。质检结果必须同时引用所依据的规则文件和被检查的目标文件，保证结论可复查。

<a id="RULE-DB-001"></a>
## RULE-DB-001 数据库表字段必须记录值域和逻辑外键

数据库按数据源、数据库、模式和表组织，一张表一个文件。每个字段必须写明名称、类型、是否可空、业务含义和值域；值域可以是枚举、范围、格式、任意值或未知。物理外键允许如实记录但不要求创建；子表字段引用主表字段时必须记录逻辑外键，并使用统一关系链接指向主表文件及字段知识编号。

<a id="RULE-IMPACT-001"></a>
## RULE-IMPACT-001 业务影响由关系分析与验收证据共同判断

文档或知识项变化后，先沿登记关系生成候选影响，再结合适用于当前项目版本的验收证据判断已覆盖场景的实际结果。证据失败可以确认相关场景受影响；证据通过只证明已覆盖场景通过，不能推翻明确的破坏性变化，也不能证明所有业务完全无影响。

<a id="RULE-IMPACT-002"></a>
## RULE-IMPACT-002 影响查询只提供三级人工决策输入

影响结果仅分为 `required`（必须处理）、`review_required`（需要复核）和 `informational`（仅供参考）。直接影响依据关系和变化类型确定；间接影响不得自动升级为必须处理；未知变化统一要求人工复核。分析命令默认只动态读取和报告；仅在破坏性变化、跨版本迁移或审计需要时，才按用户确认保存影响记录。它不能确认业务结论或控制开发任务是否执行。

<a id="RULE-AGENT-001"></a>
## RULE-AGENT-001 正式写入必须基于已确认提案

Agent 可以读取、分析并生成提案，但在创建、更新、归档、迁移或版本封存等正式写入前，必须展示目标、来源、关系、影响、冲突和验证计划，并获得用户对同一修订号的明确确认。确认前只能写入隔离的临时结果；修订内容变化后必须重新确认。

<a id="RULE-SPEC-001"></a>
## RULE-SPEC-001 需求正文唯一权威且就绪度独立

需求的业务内容只在 Markdown 正文保存，Front Matter 只保存机器身份、知识状态、规格完整度、优先级、分类和更新时间。需求规格完整度只由需求自身的问题价值、范围、稳定业务规则、成功标准、约束依赖和开放阻塞问题决定；不存在功能承接只能报告覆盖缺口，不能阻止完整需求成为 `ready`，也不能解释为已经开发。

<a id="RULE-ARCHIVE-001"></a>
## RULE-ARCHIVE-001 归档必须在替代和引用迁移后确认执行

有审计价值的正式知识只有在后继项已确认、双向替代关系已建立、其他当前引用已迁移且检查通过后，才能生成归档提案。提案必须固定源路径、归档目标、后继编号、原因、来源、时间及源文件和索引摘要；用户确认同一修订号后，操作才可将旧项改为 `archived`、移动文件并更新归档索引。目标冲突、摘要变化或校验失败时不得留下部分写入。当前知识除后继项的 `supersedes` 外不得引用归档项；无审计价值的内容只能在明确确认后删除。归档不等同于版本基线。
