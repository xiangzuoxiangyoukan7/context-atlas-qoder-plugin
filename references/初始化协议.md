# 初始化协议

## Preconditions

1. Resolve the current or user-selected project root to an absolute path.
2. Confirm it is the intended repository or project directory.
3. Derive the default project name from the final directory segment and the target `doc-<项目目录名>/`.
4. Reject an override containing separators, `.`/`..`, or a target that resolves outside the project root.
5. If the target exists, make no initialization writes. Read its README and `knowledge-base.yaml`, then enter the update workflow.

## Inspect and propose

Inspect repository manifests, build files, source layout, tests, CI, configuration examples, and existing documentation. Do not run mutating project commands. Identify every technology in use and propose its directory, purpose, commands, and unknowns for user confirmation.

读取配置前先按文件名、字段名和内容模式判断是否可能包含密码、Token、私钥、连接凭据或未脱敏个人数据。对可能含敏感值的配置只读取键名、脱敏摘要或明确安全的字段，不得使用 `cat`、完整文件读取或等效操作把原值送入会话。敏感值不进入 Proposal、工具输出或知识库；需要记录配置时只保存位置、环境变量名或脱敏占位符。

Before constructing the Proposal, obtain an explicit workspace-profile selection. If the user's invocation did not already select one, proactively present `standard` (plain Markdown knowledge base without `.obsidian/`) and `obsidian` (minimal `.obsidian/` settings and graph colors), then wait for the selection. Do not silently default the interactive workflow, infer the profile from the repository or installed applications, or treat the profile selection as confirmation of the Proposal. Always record the selected value in `project.workspace_profile`. The executor may continue accepting an omitted value as `standard` only for backward compatibility with existing low-level callers.

Before writing, present:

- project root, derived project name, and exact target;
- explicitly selected workspace profile, recorded as `standard` or `obsidian`;
- facts with sources, AI inferences, unknowns, and conflicts;
- discovered technology-stack facts and added knowledge requests;
- files to create and validation command;
- confirmation request.

完整列出每个事实、来源、状态、未知项、冲突、关系和影响。事实较多时可以分页展示，但不得用分组数量或临时文件路径替代项目责任人可见的完整内容。用户延后未知项或冲突时保留它们并记录本轮延后，不得清空。

## Materialize after confirmation

1. Create a unique staging directory inside the project root; never stage over the final target.
2. Copy `assets/templates/core/doc-project/` into staging.
3. Replace exactly `{{PROJECT_ID}}`, `{{PROJECT_NAME}}`, `{{KNOWLEDGE_BASE_NAME}}`, `{{WORKSPACE_PROFILE}}`, and `{{INITIALIZED_AT}}`; fail if any `{{UPPER_CASE_MARKER}}` remains.
4. Record each confirmed technology in the shared technology-stack document; technology discovery never creates a second knowledge base or selects a stack-specific template.
5. For `obsidian`, create only `.obsidian/app.json` and `.obsidian/graph.json`; use Context Atlas `type` property queries for colors and exclude `90-历史归档`. For `standard`, do not create `.obsidian/`.
6. Copy `assets/scripts/` and `assets/schemas/` to `.project-kb/scripts/` and `.project-kb/schemas/`.
7. Populate only confirmed initial knowledge. Keep unknown values `missing` or `proposed`.
8. Run validation against staging. Rename staging to the final target only when validation has zero issues and the final target still does not exist.
9. 从重命名后的目标直接运行 `.project-kb/scripts/agent_kb_operation.py children`，并对一个已生成稳定 ID 运行 `neighbors` 和有界 `graph`；三项均成功且 JSON 可解析后，才可报告知识库可用。冒烟失败时报告初始化产物与使用验证分别是什么状态，不得把结构检查通过表述为完整使用验证通过。

If the confirmed Proposal contains `agent_entry`, create or update only its mapped file (`AGENTS.md` for Codex, Qoder, or Trae; `CLAUDE.md` for Claude Code). Preserve all existing content and replace only the `context-atlas:begin`/`context-atlas:end` block. If the host is unknown, omit `agent_entry` and do not create either file. On failure, restore the original entry file and remove the new knowledge-base target; report the staging path and do not claim initialization succeeded.
