# 更新、冲突与归档

## Enter update mode

Read `knowledge-base.yaml`, the root README, and AI collaboration rules, then select the requirements, features, contracts, ADRs, acceptance rows, change sets, and optional task records relevant to the user's request. A current-change file or task package is context, not permission to execute. Do not reinitialize an existing target or infer current requirements from archives.

Use the Proposal and explicit-confirmation contract for every formal baseline change.

## Preserve versions

Supersession belongs to `context-atlas-revise`: it creates the successor and removes the predecessor from current authority as one revise-only operation. `context-atlas-retire` never creates a successor; it handles withdrawal without a successor and later archival of an item that revise has already superseded.

For an approved replacement performed by revise:

1. Create the new item with a new version, sources, confirmer, and confirmation time.
2. Add `supersedes: [OLD-ID]` to the new item.
3. Set the old item to `superseded` and add `superseded_by: NEW-ID`.
4. Keep the old item in place while any current reference still uses it.
5. After references and validation are clean, generate an archive Proposal containing source and target paths, successor, reason, source reference, timestamp, and file/index digests.
6. Move only after explicit confirmation of the exact Proposal revision. Change the old status to `archived`, update the archive index, validate, and roll back every write on failure.

Current knowledge may retain `supersedes: [OLD-ID]` for an archived predecessor, but must not otherwise depend on or link to archive content. Content without audit value is handled by the explicit-only `context-atlas-delete` Skill: `delete-propose` binds exact paths, digests, reasons and complete reference rewrites and preflights an isolated copy; `delete-apply` executes only after confirmation of the same revision. Archive design does not introduce a version baseline.

For conflicting evidence, retain each value and source, set `conflicted`, name `resolution_required_from`, and stop before choosing a winner.

Removing a technology from the project is an ordinary knowledge update. Propose the change, confirm it with the user, update the shared technology-stack document, and retain only history that has audit value; it never changes the knowledge-base directory or validation model.

## Sensitive information

Store configuration locations and `${ENV_VAR}` names, never values. Redact personal data. Preserve only the minimal external excerpt and a versioned reference needed for traceability.
